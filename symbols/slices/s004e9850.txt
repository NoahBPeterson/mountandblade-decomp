stride facts
------------
* rec_at: page = ((char**)l->f138d0)[i >> 4]; rec = page + (i & 0xf) * 0x5ac8.
  Writing it as `&base[(i>>4)*16 + (i&0xf)]` makes MSVC fold the page load into the imul;
  the two-step char* form produces the original's `lea ecx,[edx+ecx*4]; add eax,[ecx]`.
* `sizeof(Rec5ac8)` feeds the imul, so any layout drift shows up as a wrong constant there first.

Codegen findings
----------------
* `Table` is count +0x0, pages +0x18, f24 +0x24 (there is no field at +0x28).
  The thiscall member form gave the exact `sub esp,8 / push ebx / mov ebp,ecx` prologue.
* flush_ids / id_remove are RecList members. id_remove's receiver (ecx) is the *set* at +0x138bc --
  its probe indexes `[ecx+edx*8]` -- and it adds 0x138bc to ecx only for the tail call to int_remove.
* Chain-vs-linear: Rec5ac8::write is mostly an `out->w(...)` sequence, but several runs ARE method chains
  in the original -- write them as `out->wA(x).wB(y)` (dot-chaining on the `OutStream&` returns) rather
  than storing the `OutStream*` in a local. Storing it spills to `mov ebx,eax` (2 bytes each) and breaks
  0x4e9850. The inlined int-vector writer must loop as
  `for (unsigned i=0;;i++){ if(!v->begin) break; if(i>=(unsigned)(v->end-v->begin)) break; ... }`
  with the `if (!v->begin) n = 0; else n = ...;` count above it -- that is the shape the original inlines
  at +0x8bc and +0x59f8.
* 0x4e9850 also needs `cPairs96::write` to be `__declspec(noinline)`: with /O2 MSVC otherwise inlines it,
  which is what kept that function 31 bytes too big (and the same member was still emitted separately at
  0x4e99a0, so the original source marked it noinline too).
* Remaining 0x4e9b50/0x4e9c50/0x4e9fe0 residuals: the original emits a two-instruction `lea ecx,[edx+ecx*4]`
  + separate load for `page[idx]`; MSVC here always folds it into `add eax,[edx+ecx*4]` (probed four
  spellings: `char* base` + `*(char**)(base+idx*4)`, `char** base` + `base[idx]`, `char** slotp = base+idx`,
  and `slot`-first -- all folded). 0x4e9b50 additionally keeps the outer `this` in ebp and the RecList in
  edi where we get edi/ebx; 0x4e9fe0 spills the page pointer to ebp (an extra push/pop). 0x4ea030 differs
  only in whether `mov dword ptr [esp+0xc],eax` precedes or follows `mov edx,eax` (scheduler tie-break).
